# Pre-launch triage: card/recorder tickets vs the code, 2026-09-19

Method: each claim tested against the code, the goldens, and a live hero card render. Read-only.

## REAL

### TTP-88 — card: a prefill that came from the prompt cache is not a prefill measurement, and nothing says so
Verdict: REAL
What the ticket claims: No caveat links a high cache hit to the Prefill rate, so a second run of the same prompt quotes a flattering figure unexplained.
What the code does today: No `cached_prefill` exists anywhere in the repo. The hero prints the two numbers on unlinked rows (`Prefill 167 tok/s aggregate` vs `Prefix cache 0% hit (0/238) · warm`), and the caveat list (`internal/card/caveat.go:546-556`) has `short_prompt_for_prefill` but nothing firing on a high cache share.
Evidence: `caveat.go:93` beside an absent cache-share rule; the hero's two unlinked rows.
If REAL — the smallest honest fix: Add a `cached_prefill` figure caveat in `internal/card/caveat.go`, firing when `CacheN` is a large share of `PromptN`, threshold owned in one place like `shortPromptCount` (`caveat.go:387`). No schema change — `timings.cache_n` is already recorded.
Launch risk: high — this is the one hole through which a flattering tape is quotable by accident, exactly as filed.

### TTP-100 — Active bytes per token counts an MTP/nextn block as part of the main model's step
Verdict: REAL
What the ticket claims: GGUF `nextn.*` tensors are classified like any block and counted in `ActiveBytesPerToken` (and `NLayers`, probably `Params`), so GGUF and EXL3 cards of one model disagree.
What the code does today: `Classify` (`internal/placement/classify.go:86`) has no `nextn` case — grep for `nextn|MTP|draft` across `internal/placement` returns nothing. `NLayers` still comes straight from `block_count` (`internal/placement/gguf/gguf.go:73`); `Params` from `general.parameter_count`. None of the three symptoms has a special case.
Evidence: the empty `nextn` grep plus `gguf.go:73`; hero is Qwen (no MTP block) so no golden pins this.
If REAL — the smallest honest fix: Exclude the `nextn` layer from `NLayers` and `ActiveBytesPerToken` in `internal/placement`, verify `Params` against a real GLM GGUF header first, FAIL-first a fixture with an MTP block. Values only, no schema change.
Launch risk: medium — invisible on the current hero, but any GLM/DeepSeek GGUF card overstates active bytes and prints a wrong `L` today.

### TTP-102 — card: power draw over the decode window, not one sample
Verdict: REAL
What the ticket claims: The HOST power figure is one end-of-run sample, so "sat on the cap" and "grazed it" read identically.
What the code does today: `powerString` (`internal/card/card.go:1318-1327`) renders one `GPUSample` from `GPUsAtEnd` — the hero's "281 of 300 W" is one sample. No max-over-window reduction exists in `internal/card`, though the material is in the tape: `RunSample` already carries `GPUs []GPUSample` per sample (`internal/tape/tape.go:933-940`).
Evidence: hero HOST row; `card.go:1318`; `tape.go:936`.
If REAL — the smallest honest fix: Reduce the decode-window samples to a max draw (or fraction of samples ≥98% of limit) in `internal/card/card.go` and append it to the figure. No schema change. Keep `throttled:` until both rows exist — the ticket's thermal counter-case argues against dropping it yet.
Launch risk: medium — a capped-and-paying 150 W run and a comfortable 281/300 W run read as the same shape of line.

### TTP-103 — PlacementDevice.ActiveBytesPerToken omitempty conflates a measured zero with an unmeasured device
Verdict: REAL
What the ticket claims: A measured-zero active and a never-measured device serialise identically, so the former misreads as estimated.
What the code does today: Both fields are still `omitempty` (`internal/tape/tape.go:304,494`), and later code works around it rather than fixing it (`caveat_test.go:694`, `tape.go:827` cite TTP-103 as why a zero asserts nothing).
Evidence: `internal/tape/tape.go:304,494`.
If REAL — the smallest honest fix: Schema change, therefore the lead's: a pointer, an explicit measured flag, or a sentinel that separates "read zero" from "never looked", applied to both fields (and TTP-109 with them — decide the shape once, not twice).
Launch risk: low — costs a wrong "estimated" reading on embedding-only devices, not a wrong figure on the hero.

### TTP-109 — tape: a measured zero and an unmeasured field are the same tape — vram_kv_bytes when paged attention is off
Verdict: REAL
What the ticket claims: `VRAMKVBytes` cannot say "measured: no pool exists", so that and "never looked" are the same tape and the same `?`.
What the code does today: `VRAMKVBytes int64 json:"vram_kv_bytes,omitempty"` (`internal/tape/tape.go:508`) — unchanged, zero means unknown. No `none` value, no companion flag.
Evidence: `internal/tape/tape.go:508`; hero prints `kv ?` (hero is not a paged-off run, but the field has no third state to print).
If REAL — the smallest honest fix: Same schema-shape decision as TTP-103, for both at once. The ticket itself says it is not urgent.
Launch risk: low — a `?` where a `none` belongs, by the ticket's own words.

## PARTIAL

### TTP-91 — card: a prefill tok/s that is mostly a fixed cost is not a throughput
Verdict: PARTIAL
What the ticket claims: Prefill tok/s on an offloaded MoE box is a function of prompt length, and the card lets it be quoted as a rate.
What the code does today: The ticket's minimum option landed: the Prefill row carries the length plus the TTP-65 split — hero: `167 tok/s aggregate · 42.1 tok/s each / 238 prompt tokens · engine prefill 5649 ms / queue 56 ms`. Missing is any sentence saying the rate is a fixed cost wearing rate units. The fitted-line option is already ruled out by the ticket's own comment (two regimes, threshold in an env var toktape cannot see).
Evidence: hero Prefill row; no fixed-cost wording in `caveat.go`.
If PARTIAL — the smallest honest fix: A figure-severity caveat in `internal/card/caveat.go` stating the prefill figure is dominated by a fixed per-call cost. No schema change.
Launch risk: medium — the length is now quotable alongside, but nothing stops quoting the rate alone.

### TTP-108 — card: the aggregate rate is diluted by the tail of a ragged run, and nothing says so
Verdict: PARTIAL
What the ticket claims: The aggregate falls below per-stream × N on ragged runs and the card prints both without explaining the gap.
What the code does today: Half landed — `streamsMultiply` (`card.go:1065-1076`) plus "not all decoding at once" (`card.go:1125-1127`) is live on the text card's Streams block; the hero itself prints it. But `card.go:1101-1105` says "TTP-108 is the fuller version of this, on the caveat lines" — and that version is absent: no dilution caveat exists, the Decode row (`144 tok/s aggregate · 42.1 tok/s each`) is unqualified where the mismatch sits, and the PNG has no equivalent clause (no `streamsMultiply` in `internal/card/png/`).
Evidence: hero Streams row vs hero Decode row; `card.go:1101-1105`; empty PNG grep.
If PARTIAL — the smallest honest fix: A caveat-line wording for the Decode row plus PNG parity. The second-aggregate option is a schema change and the lead's open call.
Launch risk: medium — the README caption covers it in prose and the Streams block now names it, but a stranger multiplying the Decode row still gets 168 vs 144 with no sentence at the site of the arithmetic.

### TTP-97 — card, png: the prefill headline carries no prompt length, and a two-stream run prints a p50 and p95 that are one sample each
Verdict: PARTIAL
What the ticket claims: Prefill rate without its length, and percentile pairs over trivial sample counts.
What the code does today: Lengths arrived without the unification asked for — the PNG prints `TotalPromptN` ("N prompt tok", `png/content.go` sub2), the text card "238 prompt tokens", but neither uses the `pp279 × 2` vocabulary. The percentile predicate has not landed at all: text card (`card.go:1137-1140`) and PNG both print p50+p95 unconditionally — no shared "one TTFT when the rendered strings are equal" predicate, no table test. Hero (p50 5704 vs p95 5707) legitimately prints both, masking that the 2-stream identical case still prints both.
Evidence: `card.go:1137-1140`; `png/content.go` sub2; no equality predicate in either renderer.
If PARTIAL — the smallest honest fix: One predicate in `internal/card`, asked by all three renderers, plus the `ppN × S` label across card, PNG and bench table, with the predicate table test. The TTFT-as-headline half is a look change for the lead's look loop.
Launch risk: medium — two identical numbers still print as a pair on small runs, which reads as a bug by the ticket's own (correct) precedent.

### TTP-96 — card: cold_cache fires on a warm --lazy-mode run
Verdict: PARTIAL
What the ticket claims: The hero carries a false `cold_cache` ("4.4 maj faults/token") because `--lazy-mode` faults on novel text with all weights resident, and the rule cannot tell residency from novelty.
What the code does today: The rule is unchanged — `cold_cache` still fires purely on `s.Cache.Label == tape.CacheCold` (`caveat.go:546`), threshold still `ColdMajFaultsPerToken = 1.0` (`tape.go:79`), no lazy-mode branch, no residency input. What changed is the instance: `assets/hero.tape` is now a different take (2026-09-17 Qwen 4-stream; `cache.label = warm`, `maj_faults_per_token = 0`), so the false sentence is off the README card because the tape was swapped, not because the verdict got smarter. A warm lazy-mode run on novel text would still false-fire; no regression test pins either direction.
Evidence: `caveat.go:546`; `tape.go:79`; hero tape cache fields; hero render with no cold caveat.
If PARTIAL — the smallest honest fix: The ticket's three-part shape stands: lazy-aware verdict (measured on real tapes, not guessed), FAIL-first tests on `assets/hero.tape` (no fire) and a genuinely cold fixture (fires), evidence trail in `-o json`. Lead's design call.
Launch risk: low — nothing false on the README card today; the risk is the next lazy-mode hero re-firing it silently.
