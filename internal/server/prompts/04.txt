The report as published (report R-2026-08-70b, revision 1.2, dated 18 August):

---- begin quoted report --------------------------------------------

Arclight Inference Server 2.4.1 and the open-source engine 0.9.2
A single-node comparison on a 70-billion-parameter model in 4-bit

Prepared by Arclight Performance Labs. Results are reproducible with
the compatibility example referenced below.

Executive summary

On one eight-accelerator node, serving the same 70B chat model from
the same 4-bit weights file, Arclight Inference Server 2.4.1 completed
a two-hundred-request suite with a mean time to last token of 11.2
seconds. The open-source engine 0.9.2, started exactly as our
published example starts it, completed the identical suite with a mean
time to last token of 38.1 seconds. Arclight is 3.4 times faster on
this workload. The gap is not explained by the model, the node, the
prompt, or the request pattern, which were identical; it is explained
by the serving stack.

Test environment

Component        Specification
Node             Arclight AN-8 reference node
Accelerators     8 x 24 GB (192 GB total)
Host CPU         2 x 24-core, 2.1 GHz base
Host memory      512 GB DDR5
Local storage    3.8 TB NVMe
Operating system Arclight OS 11.4 (kernel 6.9)
Power mode       Balanced (vendor default)
Other load       None — the node is otherwise idle

Both servers ran on this node, back to back, with no configuration
change between the two runs apart from the serving software itself.

Software under test

Arclight Inference Server 2.4.1, the current stable release at the
time of writing, installed from the vendor package.

The open-source engine 0.9.2, the current stable release at the time
of writing, installed from its own release page and started exactly as
our published compatibility example starts it. We maintain this
example, arclight-examples/oss-baseline, as the recommended way to run
the engine on this hardware, and it is the configuration we would
advise a customer to deploy.

How each server was started

Arclight:

    arclight-serve --model 70b-q4.bin --all-accelerators \
                   --context 8192 --batch auto --port 881

The open-source engine, from arclight-examples/oss-baseline/run.sh:

    engine serve --model 70b-q4.bin --accelerator-count 4 \
                 --context 8192

Both commands load the same weights file from the same NVMe volume.

Methodology

A representative production prompt of about 900 tokens was used for
every request. The suite sends two hundred such requests at a
sustained concurrency of sixteen and records, for each server, the
time from sending the request to receiving the final token of the
response. We report the mean of those two hundred times. Responses
were not tokenized after generation; both servers sampled with their
own default settings, as a customer would run them. Each
configuration was run once, back to back, on a node that is otherwise
idle. The suite sends no warm-up requests; the first request of each
run is part of the measured two hundred.

Results

Metric                              Arclight 2.4.1   open-source 0.9.2
Requests completed                       200 / 200         200 / 200
Failed requests                                  0                 0
Prompt tokens per request (approx.)            900               900
Mean time to last token                     11.2 s             38.1 s
Suite wall time                           2 m 20 s           7 m 56 s
Speed-up (mean time to last token)          baseline           3.4x

Why the gap is this large

Three things in the Arclight stack compound on this workload. The
scheduler batches the sixteen in-flight requests into one accelerator
pass whenever their token positions align, where the engine schedules
each request independently. Our kernels fuse the attention and
feed-forward stages for 4-bit weights, which halves the host-side
launch count on this generation of hardware. And the engine in this
configuration re-evaluates the full shared prompt prefix on every
request, because the example's configuration leaves the engine's
cross-request prefix cache off — the default in its current release,
and the setting most of its own users run. A customer who measures
this workload on the defaults will see what we saw.

Fairness statement

The baseline was run from our published example without modification.
We consider this its recommended configuration for this hardware, and
we did not tune it, so that the numbers reflect a typical deployment
rather than a best effort. We did not disable any baseline feature;
the example's defaults apply, whatever they are. Customers are of
course free to tune the engine further and to enable its prefix cache;
a tuned baseline is a different experiment, and one we have not run.

Frequently asked questions

Why one run per configuration? The reported figure is already the mean
of two hundred requests, which averages away per-request variance.

Why mean time to last token and not time to first token? For batch
and offline workloads the total time to complete a request is what the
operator pays for. Interactive time-to-first-token results for both
servers are forthcoming in a follow-up report.

Why concurrency sixteen? This is the steady-state concurrency of a
mid-size deployment of a support workflow, which the prompt comes
from.

Can I reproduce this? Yes. The example repository contains the run
script, the suite runner, the prompt file, and the node specification
used here.

Is the quantization identical? Yes. The same 4-bit weights file was
loaded by both servers from the same volume.

What sampling settings were used? The server-side defaults of each
product, as a customer would deploy them.

Limitations

This is one workload shape — long prompt, one concurrency level, one
model size. Other prompt lengths, output lengths, and concurrency
levels will produce different ratios, in either direction.

arclight-examples/oss-baseline/suite.py

    #!/usr/bin/env python3
    """Send one prompt file n times at a fixed concurrency; time each
    request from send to its last token. Prints the mean."""

    import argparse
    import json
    import time
    import urllib.request
    from concurrent.futures import ThreadPoolExecutor


    def run_one(url, prompt):
        body = json.dumps({"prompt": prompt, "stream": True,
                           "n_predict": 256}).encode()
        req = urllib.request.Request(url, data=body,
                                     headers={"Content-Type":
                                              "application/json"})
        start = time.perf_counter()
        with urllib.request.urlopen(req) as resp:
            for _ in resp:
                pass  # consume the stream to its last token
        return time.perf_counter() - start


    def main():
        ap = argparse.ArgumentParser()
        ap.add_argument("--host", default="127.0.0.1")
        ap.add_argument("--port", type=int, default=881)
        ap.add_argument("--prompt", required=True)
        ap.add_argument("--requests", type=int, default=200)
        ap.add_argument("--concurrency", type=int, default=16)
        args = ap.parse_args()

        prompt = open(args.prompt).read()
        url = f"http://{args.host}:{args.port}/completion"
        with ThreadPoolExecutor(args.concurrency) as pool:
            times = list(pool.map(
                lambda _: run_one(url, prompt), range(args.requests)))
        print(f"requests {len(times)}")
        print(f"mean time to last token {sum(times) / len(times):.1f} s")


    if __name__ == "__main__":
        main()

The engine's own getting-started page, which the example README links to, and which is where the report's claims about engine defaults can be checked:

    Starting the engine

        engine serve --model <file> --accelerator-count N

    Common flags:

        --context N       context window in tokens, default 4096
        --batch N         maximum requests batched into one scheduler
                          pass, default 1 — each request runs alone
        --prefix-cache    reuse the evaluated prompt prefix across
                          requests that share it. Off by default; turn
                          it on when your prompts share a prefix.

And the engine's release note for 0.9.2, from the same page, which is when that default changed:

    0.9.2 — 21 July
      * --prefix-cache is now off by default. Under parallel slots a
        cached prefix could be reused from a pass computed under a
        different batch shape, which produced occasional wrong
        continuations. Pass --prefix-cache to restore the 0.9.1
        behaviour if your prompts share a prefix and you accept that
        risk.
