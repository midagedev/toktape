groups:
  - name: checkout
    rules:
      - alert: CheckoutP99High
        expr: histogram_quantile(0.99, sum(rate(checkout_request_seconds_bucket[5m])) by (le)) > 1
        for: 5m

          severity: page

          summary: checkout p99 above 1s for 5m

        labels:
          severity: page
        annotations:
          summary: checkout 5xx rate above 2% for 5m

The pull request that shipped v2.31, with the review thread that discussed the leak:

~~~
payments: retry failed confirmations on a dedicated connection (#4817)

v2.30 reuses the caller's pooled connection across confirmation
retries. After a PSP flap the connection can arrive in a half-closed
state and every retry on it fails, which cost us INC-2026-08-31
(41 stuck checkouts, 3 hours of elevated latency). This change gives
each attempt its own connection from the pool, so a poisoned
connection can no longer poison the retry.

- acquire a connection per attempt in confirmWithRetry
- release on the success path
- new counter psp_confirm_attempts_total{attempt}

Reviewer thread:

  sofia: the error path returns before the release — does anything
         give the connection back when attempt 1 fails?

  marcus: good catch. attempts are short-lived and rare, so I'd rather
          not hold a per-attempt handle; the pool reaper closes stale
          connections after idle_lifetime (10m) anyway. I'll add an
          explicit release if the pool gauges move after rollout.

  sofia: ok — ship it with the gauge, and let's watch
         api_db_pool_in_use through the canary.
~~~
