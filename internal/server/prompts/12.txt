Harden this nightly backup script, which runs from cron as root. Last week the NFS mount was missing when it ran, and it deleted files from a directory nobody expected it to touch.

List every way this script can fail or do damage, with the condition that triggers each one, including how many backups it really keeps. Then rewrite it defensively: strict mode, quoting, a check that the mount is really there, a lock so two runs cannot overlap, an exit status cron can act on, and retention that cannot delete anything outside the backup directory.

Everything the postmortem gathered is below: the script as installed, how cron invokes it, how the mount is configured, what the broken night left behind in the journal and the log, and what the directory it deleted from looked like the next morning.

The script.

It lives at /usr/local/sbin/nightly-backup, mode 0755, owner root:root, installed by hand in October 2021 and copied from host to host ever since — it is not in the configuration-management repo, and the ticket to bring it in has been open since 2023. As installed, byte for byte:

~~~bash
#!/bin/bash
SRC=$1
DEST=/mnt/backup/$(hostname)
KEEP=7

mkdir $DEST/tmp
tar czf $DEST/tmp/backup-$(date +%F).tar.gz $SRC
mv $DEST/tmp/* $DEST/
rm -rf $DEST/tmp

cd $DEST
ls -t | tail -n +$KEEP | xargs rm -rf
echo "backup of $SRC done"
~~~

Where and when it runs.

The host in this postmortem is web01, a Debian 13 box (bash 5.2, GNU coreutils 9.7, GNU tar 1.35) that carries the team's shared development homes: 41 developers, 9.2 GB under /home, growing about 40 MB a week. The schedule and the redirect live in /etc/cron.d/nightly-backup:

~~~
SHELL=/bin/bash
PATH=/usr/sbin:/usr/bin:/sbin:/bin
30 2 * * * root /usr/local/sbin/nightly-backup /home >> /var/log/nightly-backup.log 2>&1
~~~

Two sibling hosts, db01 and ci01, run the same script under their own /etc/cron.d entries, backing up /var/lib/postgresql and /srv/workspace into their own directories on the same NFS export. The export's root holds the three script hosts' directories — web01, db01, ci01 — alongside the restic repositories of web02, web03 and web04, which matters for what the retention line is allowed to ever list: a retention that escapes one host's directory does not stop at that host's backups.

For completeness, everything cron runs on this host as root:

~~~
root@web01:~# ls -1 /etc/cron.d
apt-compat
e2scrub_all
nightly-backup
php
~~~

The host's time zone is Europe/Amsterdam. On the last Sunday of October the clocks go back at 03:00 to 02:00, and 02:30 that night occurs twice; vixie cron has no duplicate-suppression for that hour. Nobody has ever checked what the script does when it runs twice in one night.

The log at /var/log/nightly-backup.log is rotated monthly by /etc/logrotate.d/nightly-backup and read by nobody:

~~~
/var/log/nightly-backup.log {
    monthly
    rotate 12
    compress
    missingok
    notifempty
}
~~~

There is no MTA on the host, so any cron output that is not redirected would be discarded; with the redirect in place, nothing mails at all, which is why three and a half hours passed between the 02:30 run failing and the 06:00 freshness alert being the first thing to notice.

What cron hands the script.

A /etc/cron.d job runs with no controlling terminal, HOME and LOGNAME set from the passwd entry of the user the line names — root, so /root — the working directory set to that home, a PATH of whatever the crontab file itself sets, and nothing else of the interactive environment: no user profile, no rc file, none of the aliases or functions an interactive root shell would have. Every command the script calls has to resolve inside that PATH, and every path it touches is either absolute or relative to /root.

How the mount is configured.

/mnt/backup is not in /etc/fstab. It is an autofs indirect mount, owned by the automounter, which is why the path exists only while the automounter is running and the map parses. /etc/auto.master.d/backup.autofs:

~~~
/mnt  /etc/auto.mnt  --timeout=600
~~~

/etc/auto.mnt, as it had been since 2021:

~~~
backup  -rw,soft,timeo=100,retrans=2  nas-01.lab.example.net:/export/backups
~~~

On Tuesday 8 September at 14:22 an Ansible push from the storage repo's automount role deployed a new version of the map to the four web-tier hosts. The template had been edited that morning to tune the NFS retry options, and a typo rode along. The map as it landed on web01:

~~~
backup  -rw,softt,timeo=100,retrans=2  nas-01.lab.example.net:/export/backups
~~~

The automounter refused it and went down, and with it the /mnt/backup mount point itself. From the journal:

~~~
Sep 08 14:22:41 web01 systemd[1]: Reloading autofs.service.
Sep 08 14:22:41 web01 automount[1487]: syntax error while parsing map /etc/auto.mnt at token "softt"
Sep 08 14:22:41 web01 systemd[1]: autofs.service: Control process exited, code=exited status=1
Sep 08 14:22:41 web01 systemd[1]: autofs.service: Failed with result 'exit-code'.
~~~

The other three web-tier hosts failed the same way, but they back up with restic from a systemd timer that checks its own mount before touching anything, and each of them reported a clean failure to the monitoring. The push reached only those four web-tier hosts, and web01 is the only web-tier host that runs this script; its siblings db01 and ci01 run it too, as root out of /root exactly as web01 does, but nobody touched their map, so their mount stayed up, their cd never failed, and nothing of theirs was ever a deletion candidate. web01 was the only one damaged.

The night it happened.

The job fired at 02:30 on Wednesday 9 September. The whole session, from the journal:

~~~
Sep 09 02:30:01 web01 cron[1781]: pam_unix(cron:session): session opened for user root(uid=0) by (uid=0)
Sep 09 02:30:01 web01 CRON[21433]: (root) CMD (/usr/local/sbin/nightly-backup /home >> /var/log/nightly-backup.log 2>&1)
Sep 09 02:30:01 web01 CRON[21433]: (cron) session closed for user root
~~~

Under a second from open to close. The log file carried no timestamps of its own — cron redirected the output, and the script prints none — so the session bracket above is the only clock these lines have. What those less-than-one-second left in /var/log/nightly-backup.log:

~~~
mkdir: cannot create directory '/mnt/backup/web01/tmp': No such file or directory
tar (child): /mnt/backup/web01/tmp/backup-2026-09-09.tar.gz: Cannot open: No such file or directory
tar (child): Error is not recoverable: exiting now
mv: cannot stat '/mnt/backup/web01/tmp/*': No such file or directory
/usr/local/sbin/nightly-backup: line 11: cd: /mnt/backup/web01: No such file or directory
backup of /home done
~~~

Read the last two lines together. The cd on line 11 failed, the script did not stop, and the very next line — ls -t | tail -n +$KEEP | xargs rm -rf — ran anyway, in whatever directory the shell was already in. It printed nothing and returned success. Then the echo reported the job done, and the script's exit status was the echo's: zero.

What directory the shell was already in.

cron starts a /etc/cron.d job in the invoking user's home directory, and this job runs as root. So the retention pipeline listed, sorted and deleted from /root. The ls in it has no -a, so the dotfiles were never listed and never deleted; everything else in /root was a candidate, sorted by modification time, everything past the six newest included.

What the loss actually was.

Of the five things deleted from /root on 9 September: docker-cleanup.sh lived verbatim in a gist and was recovered in minutes; old-id-rsa-rotation.txt was superseded and unmourned; incident-2026-05-12/ was reconstructed from the wiki export in an afternoon; pgdump-lab-2026-06-30.sql.gz held lab data regenerable from the seed scripts. training-videos/ held camera originals from two onboarding sessions and is gone; the person who recorded them left in July and the files existed nowhere else.

A good night, for contrast.

Sep 08 02:30:01 web01 cron[1781]: pam_unix(cron:session): session opened for user root(uid=0) by (uid=0)

Seven minutes forty-three seconds, start to finish, for 9.2 GB of homes to a 3.8 GB archive. On a night when nothing goes wrong, the script's only visible output is tar's warning about the leading slash and the final echo.

Two near misses already in the logs.

Thursday 3 September, the archive that was moved into place with a warning inside it. The session ran 02:30:01 to 02:41:33 and the log for that night reads:

~~~
tar: Removing leading `/' from member names
tar: /home/finance/Q3-ledger-2026.ods: file changed as we read it
backup of /home done
~~~

tar exited 1 that night. The script did not check, moved the archive from tmp into the retention set anyway, and reported done. Nobody has ever restored from a September archive, so whether that tarball is complete is unknown to this day.

Tuesday 25 August, from ticket ops-4417 rather than any log: an engineer ran the script by hand twice in one afternoon while testing a restore. Both runs wrote the same dated filename, and the second run's tar overwrote the first's while the first was still being read from the NFS export for the restore test. The script has no lock, and nothing in it noticed.

What the backups are for.

The recovery objective, from the runbook: homes are RPO 24 hours, RTO 4 hours, and the restore procedure is one paragraph — "gunzip the newest tarball from /mnt/backup/web01 on the NAS into a fresh home, chown -R the developer, tell them to check their untracked work". The repositories under /home live in remotes elsewhere and are not the point of these backups; the point is everything that is not in git: scratch branches never pushed, notebook state, VM images for the two embedded developers, GPG keyrings, and .ssh directories. The restore procedure has never been run end to end; the last attempt was the 25 August ticket above, which tested reading an archive while it was being overwritten and proved nothing else.

What the managed fleet does instead.

The three hosts the Ansible push did reach with its restic stack run the same nightly idea under systemd, and their unit is the working contrast the hand-installed script never got. From web02:

~~~
anna@web02:~$ systemctl cat backup.service
# /etc/systemd/system/backup.service
[Unit]
Description=nightly restic backup of /home
After=network-online.target mnt-backup.mount
RequiresMountsFor=/mnt/backup

[Service]
Type=oneshot
ExecCondition=/usr/bin/test -d /mnt/backup/web02
ExecStart=/usr/bin/flock -n /run/lock/backup.lock /usr/sbin/backup-restore-helper backup /home
Nice=10
~~~

It is not a proposal to adopt restic here; it is the record of which guards the managed half of the fleet already ships and this script does not.

What the script already gets right.

Two properties are worth keeping in any rewrite. The archive is built in a tmp directory and moved into place, and mv inside one filesystem is a rename, which is atomic: a reader never sees a half-written archive under its final name. And the date-stamped filenames sort lexically in date order, so anything that lists the directory gets chronology for free. Both properties survived five years of nobody looking at them, and the rewrite should not lose either without saying so.

What has already been done.

Two things were fixed in the week after the incident and are not this script's business: the map typo is corrected at the source in the storage repo's template, and the freshness alert now fires at 03:15 rather than 06:00, so a failed 02:30 run is seen within the hour. The script itself is untouched since 2021, and that is the part this task is about.
